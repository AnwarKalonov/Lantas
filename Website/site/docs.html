getting started

Installation

Requires Python 3.9+, a supported backend (NumPy, PyTorch, TensorFlow, CuPy or JAX), and a model for the agent: sign in to OpenRouter from Pulse (no key to handle, free models available) or bring an API key.

$pip install pulseml

Installing puts a pulse command on your path. Run it and Pulse takes you through setup.

Start Pulse

$python3 -m pulse

To make the plain pulse command work, add Python's scripts folder to your PATH once:

$export PATH="$PATH:$(python -c 'import sysconfig; print(sysconfig.get_path("scripts"))')" && pulse

Start Pulse

getting started

Quickstart

Three steps, and no changes to your training code.

  1. Install Pulse and run it in the folder you train in.
  2. Let it attach to the run. It reads the variables you already have, a few times a second.
  3. Ask the agent a question, or read the findings it raises while the run continues.
Nothing is installed into your loop: no sys.settrace, no callback into user code.

Supported backends

Pulse reads the values already in your training loop, so the backend decides how much it can see without extra work.

PyTorch
tensors, autograd state, optimizer state, gradients and loss
TensorFlow
tensors and metrics; Keras metrics need one line of setup in stream mode
JAX
arrays and pytrees inside the training step
NumPy
arrays and scalars, no device transfer
CuPy
GPU arrays, opt-in through /gputrack
Keras metrics live in the callback logs dict, not in local variables, so the stream monitor can't see them by sampling. See Keras.

core concepts

How Pulse works

Pulse separates AI reasoning from exact numerical calculation: instead of asking a model to estimate whether a gradient or update is unusually large, Pulse calculates the quantity directly.

Deterministic checks compute gradient and update ratios, scaling factors and normalization statistics from the tensors. When a check holds, it raises a finding with its numbers. The agent reads that evidence with your source code, proposes the smallest patch that explains the failure, and Pulse verifies the patch afterwards.

The seven stages, on the landing page

core concepts

Detection and auditing

Findings

A finding carries a check id, a variable, a severity, its numbers and a confidence. It is deduplicated on (check, variable), so "spiked to 4.12" and "4.13" aren't two problems. A check must hold for two consecutive evaluations before it is raised, except NaN and Inf, where waiting is itself the damage. Findings clear when the condition goes away and can fire again. Detection runs whether or not auto-fix is on.

When the agent looks again

After each model turn the brain asks when to come back, and why. A fix that just landed, a metric heading the wrong way or anything uncertain pulls the next look in to minutes; a smoothly descending run is left alone for an hour. A NaN, a critical finding or a fix brings the next look forward immediately, and the schedule survives a brain restart.

The audit pass

It is handed the whole run: every curve downsampled into min/mean/max buckets (a two-step spike survives), current findings, tensors, what was fixed, earlier audits, and how many samples were dropped. It is asked for what deterministic checks can't see: a loss decreasing far slower than it should, two metrics that disagree, a plausible-but-wrong value.

ML lint (mllint)

Deterministic code-level checks: incompatible loss/metric combinations, redundant activation/loss combinations, backward() without the expected optimizer update, train/eval mode issues, suspicious learning rates, and other ML-specific static patterns.

tracking

Tracking

Pick a variable. Pulse keeps six things for each one:

shape
dimensions, read without converting the tensor
dtype
float32, bf16, int64, and whatever else the run uses
device
cpu, cuda:0, and where the value actually lives
statistics
min, mean, max, and the spread, on a schedule
NaN / Inf
status, raised immediately rather than after two evaluations
history
downsampled into min/mean/max buckets so a two-step spike survives

Illustrative example, not real runtime data. GPU data is touched only on request.

tracking

GPU tracking

If nobody asks Pulse to touch the GPU, Pulse doesn't touch the GPU.

CPU-first is the default. Turn on GPU tracking for the variables you care about:

>/gputrack activations
GPU tracking can introduce device-to-host transfer overhead. It is opt-in.

debugging

Auto-fix and approver

>/autofix on

Who approves commands

Some shell commands the agent wants need an OK first: ones that delete files, rewrite git state, reach outside the project, start a background process or overwrite a file. So a long run never stops to wait, a model answers that y/N. By default it is the agent's own model, asked separately.

#in pulse_config.json
"approver": "off"# you answer yourself

Or set "approver": "<model>" to pick a different model. The same commands are flagged either way; only who answers changes.

What the approver sees and decides

Only the command, why it was flagged, the project folder, and what the agent was working on, never the agent's reasoning. It answers APPROVE or DENY with a reason that goes back to the agent. It is told to deny anything that could destroy work that can't be regenerated, touch files outside the project, handle credentials or use sudo, and to deny when unsure.

It also answers "apply this change?" for each edit the agent proposes, judging the diff against your request. Every applied change stays one /undo away. If it can't be reached, Pulse asks you (or declines in a non-interactive run). Every decision is printed and recorded in the agent log.

training machine
pulse runs next to your training script, on the box that has the GPU

Sessions · Incidents · Agent logs · Tracebacks · Commit · Team members
Cloud synchronization is best-effort and is not intended to block the training loop. For sensitive projects, review your cloud and telemetry configuration carefully.

Dashboard

Workspaces can be named and managed from the CLI; members can leave, and admins can delete one. A run opened in the app (via /run, /monitor, or attached) gets its own session, with its environment, metric snapshots, findings and crashes as incidents, the agent's turns, and uptime, synced in the background. Sign in at the dashboard to pick a workspace, then a project, then a run.

Runs show loss, grad norm, learning rate, uptime/downtime, commit, GPU and incidents. A run counts as live if it had activity in the last 5 minutes. Secret projects appear only to workspace admins and members who joined with the project's join code.

advanced

Two processes: monitor and brain

training process
pulse_monitor.Monitor reads values and writes frames. It never blocks, never thinks.
brain process
pulse_brain.Brain keeps history and detection, runs the audit and the agent.

For most cases, just use pulse. It is the better default. Stream mode is for when you want a run to keep going with nobody attached.

Pulse used to be one process, so a run stopped dead while the model thought. Measured on a 20k-step loop, PulseCLI.update() held the training thread for 84% of the wall clock, almost all of it two blocking model calls.

$pulse run --stream train.py

What the training process pays

Nothing is installed into the loop: no sys.settrace, no callback into user code. A background thread reads the training thread's variables a few times a second. It never converts data to answer a question about its shape; only 0-d and few-element values cross the device boundary, on a schedule; and it holds no references, so tracking a tensor doesn't keep it alive.

Why the stream is lossy on purpose

Under backpressure the oldest frame is dropped and the loss is recorded, so the brain knows its view has a hole rather than the loop being slowed. It is an append-only file, not a socket, so the brain can attach late, crash or restart without the run ever waiting.

reference

Troubleshooting

pulse not found

Add Python's scripts folder to PATH (see Installation), or use python3 -m pulse.

The app doesn't open

Pulse falls back to line-by-line screens without a real terminal (a pipe, CI), on a very small one. On Windows it needs a console that understands escape sequences: Windows Terminal, or the console of Windows 10 and later.

Keys and secrets

Don't put API keys in source code or commit them. A pasted key is never written to disk.
